Eval round 2 · Save My Eyes · 3 runs per arm

Does the copywriting skill change what an agent writes?

Six unsupervised instances rewrote the Settings labels and the long-break ideas of Save My Eyes and wrote a headline. Three had the copywriting skill with its new interface-text reference. Three did not.

Without the skill, runs 1 to 3With the copywriting skill, runs 1 to 3

Key differences

  • The slider label keeps its meaning: 3 of 3 with the skill, 0 of 3 withoutEvery skill run still says what is being delayed: breaks. Every baseline run dropped it, the same failure as round one.
  • The skill arm leaves passing text aloneBaseline runs changed 16 to 17 settings strings each, including a button, a notice title, the credits and a helper text nobody asked about. Skill runs changed 10 to 13 and none of those.
  • The baseline caught one accuracy issue more oftenThe first slider sets the gap between all breaks, not only short ones. 3 of 3 baseline runs fixed that. Only 1 of 3 skill runs did.
  • Verbs and house style survive with the skillThe sound switch kept its verb in 3 of 3 skill runs against 1 of 3. Skill runs kept the ideas' no-period style and roughly their length; baseline ideas grew about 30% and gained periods the short-break ideas do not have.
  • Headlines: safer and more uniform with the skillAll three skill headlines share one shape built on the default numbers and the screen cover. The baseline ranged wider, including one promise that only holds after a switch is turned on.
  • Small sample, and the baseline was not skill-freeThree runs per arm is enough to see a pattern, not to measure one. Two of the three baseline runs invoked the installed design:ux-copy skill on their own.

The label that started this: “Pause breaks after a call ends”

In round one both arms shortened it into a vague noun phrase. The skill now carries an interface-text reference with a keep-every-slot rule. Each rewrite below is checked for the three things a reader needs, plus whether it matches what the code covers.

Headline for the app

Each instance got only a general description of the app, was told to read the code, and was kept away from the README and the product docs.

Without the skill

  • 1Every 20 minutes, a 20-second break for your eyes.9 words. Built on the default interval and break length.
  • 2A break for your eyes every 20 minutes, never in the middle of a call.15 words. The second half is only true once the user turns on a switch that is off by default; the run said so itself.
  • 3Every so often, your Mac covers the screen so your eyes can rest.13 words. Names the mechanism, but “every so often” gives no number.

With the copywriting skill

  • 1Every 20 minutes, your Mac covers the screen for 20 seconds so you actually look away.16 words. Default numbers plus the mechanism; “actually” gives it an edge.
  • 2Every 20 minutes, your screen covers itself for 20 seconds so your eyes can rest.15 words. Same shape; “covers itself” is slightly odd.
  • 3Every 20 minutes, your Mac covers the screen so your eyes can rest.13 words. Same shape without the break length.

Key differenceThe three skill runs converged on one shape: a number from the default settings, the mechanism (the screen gets covered) and the benefit. Every claim in them holds with default settings. The baseline varied more: one tight line, one that promises something that is off by default, one with no number. For range to pick from, the baseline gave more. For a line that is safe to ship unreviewed, the skill arm did.

How this was run

  • Six fresh instances on the same model and effort, each in its own detached worktree of save-my-eyes at e82f144, the latest master on GitHub. The prompt was identical; the skill arm additionally loaded the copywriting skill by reading its files, because the installed plugin does not include it yet.
  • Each instance did all three tasks in one go, so one task may have coloured the next inside an instance.
  • Instances were told to learn the app from the Swift sources and not to read the README, PRODUCT.md, DESIGN.md or docs.
  • Everything shown comes from the git diff of each worktree. The main checkout and the other worktrees were verified unchanged afterwards. Test results are what each run reported; they were not re-run.
