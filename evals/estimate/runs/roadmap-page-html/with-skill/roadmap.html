Q1 candidates: complexity estimates

Each candidate is sized by complexity, not time: how much is unknown, how much has to move together, and how it releases. There are three levels and no hours, days or points behind them.

Judged from the one-line descriptions, without reading the code. A look at the code may move a level.

Proposed split: move file uploads to S3

Cut by release step, so every slice goes through upload, storage and download and can be released and checked on its own. This is a proposal; no tickets change until the team agrees.

  1. Uploads in one internal project are stored in and served from S3, behind a flag moderate

    Answers the open question of how file links and access rules work on S3, while both storages run side by side.

    Depends on nothing.

  2. Every new upload goes to S3 simple

    The flag from slice 1 opens to everyone. Existing files are still served from our own server.

    After 1.

  3. The roughly 40k existing files are moved to S3 in batches moderate

    Each batch is copied, checked and switched over, with a way back per batch.

    After 2.

  4. The old upload storage and its code path are removed simple

    Nothing reads from our own server any more, so this is a deletion in one system.

    After 3.

How to read the levels

simple
Known goal, no moving parts, one system changes, ordinary release.
moderate
Known goal, a few risks at most, some moving parts. The size of a typical ticket.
complex
Known unknowns, a coordinated release, several systems affected. Usually it should be split.
